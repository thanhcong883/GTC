A UX teardown of MindPal · build → run

01

The problem: no two nodes ever run at once

Stated precisely, because it changes how credible the critique is: MindPal has no intra-run node concurrency. Inside a single workflow, nodes always run nose-to-tail — even when the canvas draws a fan-out. It does run many separate runs at once (Bulk Run, Background Mode) — so the infrastructure can parallelize; the gap is specifically the independent branches inside one run. That framing matters: this isn't "MindPal can't", it's "MindPal doesn't, in the one place it would help most."

The consequence is a single rule of thumb: the value of adding parallelism is proportional to how big the independent fan-out is. So the honest question is never "is parallel good?" — it's "how much of this workflow is an independent fan-out?"

When missing it hurts
Scatter–gather / fan-outA panel, a jury, an ensemble of critics. Time = sum of N, not the slowest.
Multi-source enrichmentCall several APIs / knowledge bases, then merge. Serial = every network wait added up.
Broadcast / variantsOne input → 5 languages, 5 ad variants. Embarrassingly parallel.
Ensemble / voting · independent loopsRun N models on one input; iterate a list of unrelated items.
When it doesn't matter
Linear chainsDraft → edit → format → publish. Each step eats the last — can't and needn't parallelize.
Short workflows (1–3 nodes)Latency is already low; coordination overhead outweighs the gain.
The synthesis tailA node that gathers results is defined by waiting for them. Never parallel.
Ordered side-effectsWebhook / Payment / writes to the same record. Here serial is a safety feature.
The deepest harm isn't speed — it's design distortion. Because fan-out is slow, users avoid it: they collapse seven specialist agents into one mega-prompt to dodge the wait, losing the independent reasoning that multi-agent exists for. The missing feature quietly lowers the quality of what people build, not just how fast it runs.
A pocket formula for severity: harm ≈ fan-out width × per-node latency × run frequency × user-facing-ness. When all four stack, it's a disaster; when only one does, ignore it.

03

The redesign — let the seven run together

One change carries it: the seven independent reviewers move into a single parallel lane and collapse to their slowest member (Finance, 19s). Red Team and Chair stay sequential — they must, they synthesise everything before them. Same axis as above; the shaded stretch on the right is time handed back.

Modelled from the measured run: lane = slowest lens 19s · tail = 24s + 17s · ~15s overhead across 3 stages → ~1:15.

Before

  • Canvas draws parallel, engine runs serial — nothing says so
  • 7 independent lenses forced into a 119s queue
  • No way to opt out of the wait — the run just takes 3× longer than it needs to

After

  • A parallel lane you opt into — the product states the truth and asks first
  • Lane collapses 119s → 19s; run drops to ~1:15 (2.5×)
  • Cost shown before the burst; a defined policy when a branch fails keep control
The three changes — wireframes

Speed comes from change 1. Changes 2–3 exist because going parallel takes away two things serial gave for free: a natural point to cancel before spending, and a clear failure. Each card names the pain it repays.

Try it — the redesign, running

A working concept of the parallel mode, dropped into a MindPal-style builder. Toggle Serial ↔ Parallel and the workflow redraws itself — a straight chain (today) versus a fan-out (proposed) — then hit Run to watch it execute. Latency is simulated (the measured node times, sped up), but the scheduler, the concurrency limit and the dependency-aware join are the real thing.
