Memory & context architecture for long-running agentsKiến trúc memory & context cho agent chạy dài hạn

The agent didn't forget. Nobody decided what it should remember.Agent không quên. Chưa ai quyết định nó nên nhớ điều gì.

An agent that runs for days does not fail because storage ran out. It fails because it can no longer tell which of the things it knows is still true — and because the thing that assembles its context has no opinion about that. This is a design for the missing component: memory is governed state, and context is a view compiled for one step, under a credit and latency budget. The compiler below is real and runs in this page.Một agent chạy nhiều ngày không thất bại vì hết chỗ lưu. Nó thất bại vì không còn phân biệt được điều nào nó biết vẫn còn đúng — và vì thành phần lắp ráp context không có chính sách để phán quyết. Đây là thiết kế cho thành phần còn thiếu: memory là trạng thái dài hạn có quản trị; context là một working set được biên dịch riêng cho từng bước chạy, dưới ngân sách credit và latency. 01Memory is governed state. Context is a compiled view.

Three words get used interchangeably and should not be. History is the raw record of what happened. Memory is the curated, versioned state derived from it. Context is the much smaller thing you hand a model for one step. A vector database is a retrieval mechanism, not a memory architecture, and chat history is one input to memory, not memory itself.

Once those are separate, the interesting question stops being "how do I store this" and becomes "who is allowed to say this is true, and is it still true now". That is a governance question, and it is why this design is shaped like a compiler rather than a database: a compiler has a type system, refuses to build when types don't check, and emits a receipt of what it did.

Three constraints that are specific to PAL

A memory architecture that is correct in the abstract can still be unshippable here. Three properties of the platform decide the design:

ConstraintWhy it changes the design
Credit couplingdesign input Memory operations are billed in the same currency as the user's work. A memory writer that classifies every event, a reranker on every step, a summarizer at every checkpoint — each is an LLM call competing with the thing the customer actually asked for. A design that is theoretically correct and eats the contribution margin is not a feature.
Sequential executiondesign input Nodes run one at a time, so every millisecond of context assembly lands on the critical path. There is no parallelism to hide it behind. This is why the cache below is versioned per namespace rather than globally, and why compilation happens at memory-aware boundaries rather than at every node.
Free-tier first impressionsdesign input The cheapest memory mode is the one running while a new user is deciding whether the product works. So the cheap mode cannot be "no memory" — it has to be the mode that still guarantees approvals and constraints survive, and drops only the expensive parts.

Three failures worth separating

These get collapsed into "context rot", which then means everything and therefore nothing:

NameWhat it isWhat fixes it
Context-length degradationThe model gets worse as the prompt gets longer, independent of content.Send less. Compile a working set instead of appending history.
Memory rotStored memory goes stale, contradicts itself, or is corrupted by a summary.Versioning, expiry, supersession, provenance, authority.
Compiled-context failureMemory is correct, but the assembler picked or packed the wrong subset.Deterministic ordered selection, a lint pass, and a receipt you can audit.

The rest of this document is mostly about the third, because it is the one nobody builds a component for.

01Memory là trạng thái có quản trị. Context là một view được biên dịch.

Ba khái niệm thường bị dùng lẫn lộn. History là bản ghi thô của những gì đã xảy ra. Memory là trạng thái đã được tuyển chọn, chuẩn hóa và version hóa từ history. Context là phần nhỏ hơn nhiều được đưa vào model cho đúng một bước suy luận. Vector database chỉ là một cơ chế retrieval; chat history chỉ là một nguồn đầu vào của memory.

Khi tách ba lớp này, câu hỏi không còn là “lưu thế nào?” mà trở thành “ai có quyền nói điều này là đúng, và nó còn đúng ở thời điểm hiện tại không?”. Đó là bài toán governance. Vì vậy thiết kế có hình dạng của compiler: có hệ kiểu, từ chối build khi type không hợp lệ và phát hành receipt giải thích chính xác những gì đã làm.

03What gets remembered, and as what

Not every model output becomes a fact. The write path classifies into namespaces that differ in who may write them, how long they live, and whether they may ever be compiled as an active constraint.

Namespaces. The split is by governance, not by data type — that is the whole point.
NamespaceHoldsWritten byCompiled as
approvalsDecisions with an authorizing eventUser or policy onlyPinned
constraintsStanding rules the work must satisfyUser or policy onlyPinned
artifactsReferences, checksums, locations — never file bodiesToolsRetrieved
episodicWhat happened: attempts, failures, observationsModel or toolsRetrieved
preferencesDurable stylistic and working preferencesModel, on repetitionDecayed

What to remember

  • Approvals and rejections — verbatim, with the authorizing event id. Highest authority, longest life.
  • Active constraints — stated requirements, stored extractively so the original wording survives.
  • Decisions — what was chosen and why, with what it supersedes.
  • Artifact references — id, revision, checksum, location, and a short structural summary. Remember where the content is, not the content.
  • Meaningful episodes — a failure and its cause, not the whole log that produced it.
  • Durable preferences — only on repetition or explicit confirmation, and with confidence that decays.

Deliberately not stored: small talk, intermediate drafts past their successor, raw tool logs, and anything secret. Credentials are referenced through a broker, never copied into memory — a secret written into memory is replayed into every future session that reads it.

03Nhớ điều gì, và nhớ dưới kiểu nào

Không phải output nào của model cũng trở thành fact. Write path phân loại memory vào các namespace khác nhau về quyền ghi, vòng đời và khả năng được compile thành active constraint.

Namespace được tách theo governance, không phải theo data type.
NamespaceNội dungAi được ghiCách compile
approvalsDecision có authority eventUser hoặc policyGhim
constraintsQuy tắc bắt buộc còn hiệu lựcUser hoặc policyGhim

Nên nhớ gì

  • Approval và rejection — lưu nguyên văn cùng authority event id. Authority cao nhất, vòng đời dài nhất.
  • Active constraint — yêu cầu bắt buộc, lưu extractive để giữ nguyên wording.
  • Decision — điều đã chọn, lý do và record bị supersede.
  • Artifact reference — id, revision, checksum, location và structural summary. Nhớ nơi tìm nội dung, không nhét nội dung vào memory.
  • Episode có ý nghĩa — failure và nguyên nhân, không giữ toàn bộ log.
  • Preference bền vững — chỉ lưu khi lặp lại hoặc được xác nhận, với confidence giảm dần.

Cố ý không lưu: small talk, intermediate draft đã có successor, raw tool log và secret. Credential chỉ được tham chiếu qua broker; copy secret vào memory đồng nghĩa replay secret vào mọi session tương lai đọc record đó.

Write path ở production

event → parse typed event → extract candidate → validate schema → resolve claim identity → detect duplicate/conflict → attach provenance → commit record + namespace version trong cùng transaction → enqueue indexes

Writer dùng idempotency key từ eventId + policyVersion. Event đến sai thứ tự không sửa history; nó tạo revision mới và chạy lại supersession. Embedding và summary là derived indexes có thể rebuild, không phải source of truth.

04The compile path

Ten ordered steps. There is no weighted priority score, and that is a deliberate choice: a formula that multiplies relevance by freshness will quietly zero out an approval that is old but still binding. Ordered rules are explainable, debuggable, and produce the same answer twice.

compile path 1. scope and ACL filter tenant, workflow, permission 2. block tombstoned deleted is deleted, first 3. partition active/historical superseded and stale step aside, not away 4. validate authority evidence ← where the $50,000 error dies 5. pin approvals and constraints ← where recall survives step 200 6. retrieve remaining candidates hybrid, only for what is left 7. type and conflict lint 8. deduplicate, pack to budget 9. build capsule + overlay 10. emit CompileReceipt

Lifecycle partition happens before authority pinning (3 before 5). Reverse them and you can pin an approval that was superseded last week — the record is approved, it just is not current any more.

Superseded and stale records move to a historical pool, not to the bin. They may never be compiled as an active constraint, and they must remain reachable for audit and for explaining how the current state was reached. Scenario B is exactly this distinction.

Retrieval

Retrieval runs at step 6, on what is left after governance has had its say — which is the opposite of the usual arrangement, where a similarity search runs first and governance is applied, if at all, to whatever it returned. Hard filters (tenant, ACL, lifecycle) are not ranking signals. They are gates.

Freshness is used for exactly three things: choosing between two external observations of the same fact, ordering revisions inside one authority tier, and triggering a refresh. It is never allowed to make a current approval lose to a recent note.

The linter blocks two things, and only two

ConditionResponse
Unauthorized promotion into an active decision or constraintHard block
Two incompatible active approved decisionsHard block — ask, never pick silently
Approved decision vs. a model inferenceKeep the decision, quarantine the inference
External fact past its validUntilRefresh, or admit with a staleness marker
Conflicting low-stakes preferencesTake the newer, do not interrupt
Optional context missingContinue, degraded

The temptation is to block on every conflict. That produces a system which interrupts constantly and gets configured off within a week. Blocking is reserved for the cases where proceeding would mean acting on authority nobody granted.

Production guarantees at the boundary

ConcernGuaranteeMechanism
Snapshot consistencyOne compile never mixes namespace revisionsRead a version vector at start; retry if a pinned namespace changes before receipt commit
Idempotent writesRetries do not create duplicate factseventId + policyVersion idempotency key and claim-level uniqueness
Out-of-order eventsHistory is append-only; current state remains explainableCreate a revision, rerun supersession, never rewrite the source event
Index driftEmbedding and summaries can be rebuilt without changing truthStructured memory is source of truth; indexes carry model and policy versions
Failure recoveryA failed compile cannot partially publish contextReceipt and packet commit atomically; last valid packet remains available in degraded mode

These are architecture guarantees, not claims that the browser fixture implements a distributed store. The fixture verifies selection policy; a production implementation still has to prove these properties under concurrent writes.

04Đường compile

Mười bước có thứ tự. Không dùng weighted priority score: công thức nhân relevance với freshness có thể vô tình đưa một approval cũ nhưng còn hiệu lực về gần 0. Ordered rules giải thích được, debug được và cho selection có thể tái hiện với cùng snapshot, policy và candidate set.

compile path 1. scope và ACL filter tenant, workflow, permission 2. chặn tombstoned deleted là deleted, xử lý đầu tiên 3. tách active / historical superseded và stale rời active context 4. kiểm tra authority evidence ← chặn lỗi $50,000 5. ghim approval và constraint ← giữ recall tới bước 200 6. retrieve candidate còn lại hybrid, sau governance 7. lint type và conflict 8. deduplicate, pack theo budget 9. build capsule + overlay 10. phát hành CompileReceipt

Lifecycle partition phải đứng trước authority pinning. Đảo thứ tự sẽ ghim một approval đã bị supersede. Record superseded và stale đi vào historical pool để audit, nhưng không được compile thành active constraint.

Retrieval

Retrieval chỉ chạy ở bước 6, sau khi hard gate về tenant, ACL và lifecycle đã loại candidate không hợp lệ. Freshness chỉ dùng để chọn giữa external observation cùng authority tier, sắp xếp revision và kích hoạt refresh. Nó không được khiến một approval hiện hành thua một note mới hơn.

Chặn mọi conflict sẽ tạo một hệ thống liên tục hỏi người dùng và nhanh chóng bị tắt. Chỉ hard-block khi tiếp tục đồng nghĩa hành động bằng authority chưa từng được cấp.

05Remember, compress, supersede, delete

"Forget" is four different verbs, and conflating them is the most common design error in this area. Three of them are reversible and cheap. One is neither.

VerbMeansReversible
RetainKeep as-is, compile when relevant—
CompressKeep a shorter form that still links to its sourceYes — rebuild from source
SupersedeA newer authorized record replaces it; the old one becomes historicalYes — history is intact
DeleteTombstone the source and cascade to everything derived from itNo

How to compress

Three levels, applied by what the content is, never by how big the context has got:

  • Lossless — deduplicate by claim, normalize, replace file bodies with references. Always safe, no model call.
  • Extractive — keep the original sentences for figures, deadlines, constraints, decisions and rejection reasons. The wording is the evidence; paraphrasing it is what loses it.
  • Abstractive — a model rewrites a span of episodes into a summary. Only at checkpoints, only for episodic content, and never as the sole carrier of a constraint.
The rule the measurement changed

The intuition was that damage accumulates through repeated summarization — summary of summary of summary. The experiment in section 9 says otherwise: when a constraint was lost, it was lost on the first abstractive pass, and the number barely moved afterwards.

So the rule is not "avoid summarizing summaries". It is stronger and simpler: never let an abstractive summary be the only thing carrying a constraint. In this narrow experiment, 35% of chains dropped the figure on the first pass and one condition reached 45% by generation 3.

When to forget

MemoryPolicy
Working stateDropped at run end; kept 24–72h for debugging Proposed
Intermediate draftsCompressed once a successor is approved
Approvals and decisionsNever expire on disuse. Only revoked or superseded, and only by equal-or-higher authority
PreferencesConfidence decays without reconfirmation; never hard-deleted for staleness
External factsCarry validUntil; on expiry become stale, refreshable, never silently current
Tool errorsCompressed into a failure pattern, not kept as raw logs
PIIMinimum necessary, never propagated into derived summaries, hard-delete cascade on request

The distinction that matters: a deadline of 30 August should not disappear because nobody queried it for a fortnight. On 31 August it should stop being an active constraint. Those are different mechanisms — disuse is not expiry.

05Giữ, nén, thay thế và xóa

“Quên” thực ra là bốn động từ khác nhau. Ba thao tác có thể đảo ngược và rẻ; một thao tác thì không.

Động từÝ nghĩaĐảo ngược

Nén như thế nào

  • Lossless — deduplicate theo claim, normalize, thay file body bằng reference. Không cần model call.
  • Extractive — giữ câu gốc cho con số, deadline, constraint, decision và rejection reason.
  • Abstractive — model viết lại episode tại checkpoint; không bao giờ là nơi duy nhất mang constraint.
Quy tắc đã thay đổi sau measurement

Trực giác ban đầu cho rằng lỗi tích lũy qua summary-of-summary. Kết quả ở phần 9 cho thấy khi figure bị mất, phần lớn mất ngay ở pass đầu; các generation sau thay đổi rất ít.

Vì vậy quy tắc mạnh hơn là: không để abstractive summary trở thành nơi duy nhất mang constraint. Trong thí nghiệm hẹp này, 35% chain bỏ figure ngay pass đầu; neutral condition đạt 45% ở generation 3.

06The type system

Every record carries three independent axes. Collapsing them into one status field is what makes the $50,000 error invisible.

governanceStatusunreviewed · pending · approved · rejected · revokedWhat standing does it have?
lifecycleStatusactive · stale · superseded · tombstonedIs it still current?

The sentence this whole design exists to make true

Summary drift is not a summarization defect. It is a type error: a proposal was compiled as an approval with no authority event to license the cast. Once it is a type error, a compiler can refuse it — which is what the linter does, by name, with a span pointing at the sentence that was never authorization in the first place.

07Cache, and the one deletion that is real

Compilation on every node would put its whole cost on the critical path, which sequential execution has no way to hide. So the compiled packet is cached — but a single global memory version would be self-defeating, because a long-running agent writes memory constantly and would invalidate its own cache on every step.

Versions are therefore per namespace:

dependency fingerprint constraints@v7 approvals@v3 preferences@v4 ← stable capsule, changes rarely episodic@v481 ← overlay, changes constantly writing an episodic note bumps episodic@ only the constraints capsule stays valid and is reused

The slices that are most expensive to compile are also the ones that change least, so the hit rate is high exactly where it pays. The metrics worth publishing are not just hit rate but false cache hit and stale-cache leakage — a cache that serves a superseded constraint quickly is worse than no cache.

Hard delete is the only irreversible verb

A PII fact does not sit in one place. It is in the raw event, in an embedding, in a summary, in a summary of that summary, and in a cached packet. Deleting the source and calling it done leaves the data in every derived artifact.

This is where the rule from section 5 — every summary links back to its sources — stops being hygiene and starts paying. Because lineage is recorded as typed references, the cascade is mechanical: tombstone the source, walk derivedFrom in reverse, invalidate every derived record and cached packet, rebuild what can be rebuilt from surviving sources, and emit a deletion receipt. Scenario C in the compiler above runs this cascade for real — it is not a diagram of a cascade.

Production boundary

Backups, immutable audit logs and external vector stores need their own retention schedule. A DeletionReceipt is complete only after every active store acknowledges it; backup copies may truthfully remain pending_expiry rather than pretending deletion is instantaneous.

07Cache và thao tác xóa duy nhất là thật

Compile tại mọi node sẽ đưa toàn bộ cost lên critical path của PAL. Vì vậy context packet được cache. Nhưng một global memory version sẽ tự phá cache vì long-running agent ghi episodic memory liên tục.

Version được tách theo namespace:

dependency fingerprint constraints@v7 approvals@v3 preferences@v4 ← stable capsule, ít đổi episodic@v481 ← local overlay, đổi liên tục ghi một episodic note chỉ bump episodic@ constraints capsule vẫn hợp lệ và được dùng lại

Chỉ compile tại memory-aware boundary. Code node và deterministic tool node không cần full memory compilation. Worker dùng chung global capsule nhưng có local overlay theo task. Metric cần đo không chỉ là hit rate mà còn false cache hit và stale-cache leakage.

Hard delete là động từ không thể đảo ngược

Một PII fact có thể xuất hiện trong raw event, embedding, summary, summary-of-summary và cached packet. Chỉ xóa source vẫn để dữ liệu tồn tại trong derived artifact.

Vì mọi summary đều lưu lineage, cascade trở thành thao tác cơ học: tombstone source, đi ngược đồ thị derivedFrom, invalidate derived record và cache, rebuild từ source còn sống rồi phát hành DeletionReceipt. Scenario C chạy cascade này trên fixture store thay vì chỉ vẽ sơ đồ.

Production boundary

Backup, audit log bất biến và external vector store cần retention schedule riêng. DeletionReceipt chỉ được đánh dấu complete khi mọi active store đã xác nhận; backup có thể ở trạng thái pending_expiry thay vì giả vờ đã biến mất ngay lập tức.

09Evaluation

Two evaluations, measuring two different things, labelled differently on purpose. Neither is a claim about how good an agent is; they are claims about whether the compiler obeys its own policy, and about what a real model actually does to a hedged claim.

Does the compiler obey its policy as the run gets long? Verified

The chart is computed by the engine on this page, right now, over the fixture store — not read from a file. The comparison is against naive: a recency-ranked assembler with no lifecycle partition, no authority validation and no pinning, which is what most implementations actually are.

Does a real model promote a hedged claim? Measured

A meeting transcript contains one sentence engineered to be at risk — "we may consider a budget of up to $50,000 … nothing is signed off". A real model summarizes it, then summarizes its own summary, three generations deep, twenty independent chains per condition. The second condition uses an adversarial prompt that explicitly asks what was decided.

The hypothesis was wrong

Promotion did not happen once in 40 chains. Not in the neutral condition, and not when the prompt explicitly asked what had been decided — which demonstrably changed the framing ("it was decided to implement…") while still writing "a pilot budget of up to $50,000 pending finance committee approval". Wilson 95% CI [0%, 16.1%] per condition: this rules out a promotion rate above roughly 16%, not promotion itself.

What failed instead was omission. Between 7 and 9 of 20 chains dropped the figure entirely — the constraint was not distorted, it silently vanished. And it vanished on the first summary, not through accumulation.

So the authority linter in section 6 stands as a governance requirement — a system must not let a proposal become an approval without an authorizing event, whatever a given model happens to do unprompted — but it is not empirically motivated by these runs, and this page does not pretend it is. What the runs do motivate is extractive handling of constraints, which is now the stronger claim of the two.

Method, scoring rule, the pilot that caught a false positive in that rule before the measured runs, every raw request and response, and the derived cost are all published in METHOD.md.

10Limitations

  • The compiler here runs on authored fixtures. Conformance is VERIFIED, never MEASURED — it proves the engine obeys the policy written for it, and says nothing about how good an agent using it would be.
  • Engine time is not compile latency. The milliseconds reported by the workbench are real browser milliseconds for a JavaScript function over an in-memory array. A production compiler adds approximate vector search, reranking and possibly an extraction call. The 800 ms figure a real deployment should hold itself to is a target, not something this page measured.
  • Semantic relevance is a fixture. Scores are declared in the store, not produced by an embedding model. Pretending otherwise in a browser would be theatre.
  • The credit ceilings are proposed policy. 0% / 5% / 15% are starting values chosen to be argued with, not results.
  • The drift experiment is narrow. One model, one transcript, one hedged sentence, three generations, twenty chains per condition. A different model, a longer chain, or a source sentence with a weaker hedge could all produce a different answer.
  • Reproducible build is not determinism. The claim is that the same snapshot, policy version and candidate set yield the same selection digest. Approximate vector search, a model summarizer and embedding drift all break anything stronger.
  • Not built: multi-tenant isolation beyond a scope filter, the memory writer's own classification path, and any live-agent quality measurement Out of scope.

Thesis: memory is governed state; context is a task-specific compiled view.

Proof: the interactive compiler emits an explainable receipt and keeps all three active constraints through 200 fixture steps; the separate model experiment shows omission, not promotion, as the observed summary failure.

Boundary: fixtures verify policy behavior. They do not measure live-agent quality, production retrieval latency or distributed consistency.
