Tối giản nhưng chạy thật · loop, tools, memory

Memory của agent không chỉ nên lưu sự kiện. Nó nên lưu cả kỹ năng.

Đề bài: build một agent runtime tối giản nhưng chạy thật — orchestration loop, tool-calling, và memory — đủ để hoàn thành một task nhiều bước. Đã build xong, rồi đẩy thêm một bước: khi tool có sẵn không làm được việc task cần, agent tự viết một tool mới cho chính nó, dùng ngay ở bước kế tiếp, và giữ lại cho các session sau. Một dòng trong loop là toàn bộ khác biệt giữa việc đó chạy được và tool đó vĩnh viễn vô hình.

01 — Vòng lặp

Một API stateless, biến thành thứ tự hoàn thành một task

LLM API là stateless: gửi messages, nhận về một reply. Runtime là lớp mỏng biến một reply đơn lẻ đó thành công việc tự động, nhiều bước — gọi model, nếu nó yêu cầu một tool thì chạy tool đó, đưa kết quả trở lại, rồi gọi tiếp. Lặp lại tới khi model không còn yêu cầu tool nào nữa hoặc chạm step cap.

thêm task của user vào working memory
lặp tối đa max_steps lần:
    response = model(system, messages, tools)
    append response vào working memory            # TRƯỚC KHI hành động theo nó
    nếu response không yêu cầu tool nào:
        return text của nó                        # model đã xong
    với mỗi tool model yêu cầu:
        result = chạy tool đó
        gom một tool_result (mang theo id của tool)
    append TẤT CẢ result thành MỘT user message
dừng: chạm max_steps                               # đảm bảo có điểm dừng

Điểm xoay là stop_reason của model. "tool_use" nghĩa là model dừng lại để yêu cầu một thứ gì đó; bất kỳ giá trị nào khác nghĩa là nó đã đưa ra câu trả lời cuối cùng. Loop này được viết tay thay vì dùng tool-runner có sẵn của SDK nhà cung cấp — mục đích của bài tập là chứng minh harness được hiểu tới nơi tới chốn, và tự sở hữu loop mới cho phép có step cap, trace từng bước, và kiểm soát hoàn toàn lỗi tool.

02 — Tool Interface

Bốn field, và lỗi không bao giờ làm sập loop

Một tool gồm một name, một description (field mà model thực sự đọc để quyết định khi nào gọi), một JSON Schema cho argument, và hàm Python thực hiện công việc. Một registry biến các tool đã đăng ký thành schema list mà API cần, và dispatch lời gọi theo tên.

Lỗi là data Không bao giờ có exception lọt vào loop

File không tồn tại, argument sai, tên tool không rõ, một exception bị raise — tất cả trở thành ToolResult(is_error=True), đưa trở lại như một tool result bình thường mà model đọc được và tự phục hồi.

Sandbox tại một điểm nghẽn duy nhất Không path nào thoát khỏi workspace

Mọi file tool resolve path do model cung cấp so với một root cố định và từ chối bất cứ thứ gì thoát ra khỏi đó. Calculator là một AST evaluator chỉ whitelist — không name, không builtin, không __import__.

03 — Memory

Working memory là context. Long-term memory là knowledge.

Gộp chung hai khái niệm này là một lỗi thường gặp, nên chúng được tách riêng. Working memory là transcript đang chạy của task này — lượt của user, lượt của assistant, tool result, theo đúng thứ tự. Vì API là stateless, list này chính là cuộc hội thoại; nó lớn, ngắn hạn, và được build lại cho mỗi task.

Long-term memory là một key/value store nhỏ, lưu xuống JSON trên đĩa, do chính model quản lý qua hai tool remember / recall, và được render vào system prompt lúc khởi động — nên agent bắt đầu mỗi session đã sẵn biết những gì nó học được trước đó. Một fact lưu ở session này recall được bởi một instance Memory hoàn toàn mới ở session sau; điều này đã được test, không phải giả định suông.

04 — Self-Extension

Tool surface lớn dần giữa task — và lý do nằm ở một dòng

Một meta-tool, create_tool(name, description, input_schema, code), cho phép agent cung cấp một định nghĩa tool cùng chính phần code Python triển khai nó. Runtime kiểm tra code, thực thi nó, đăng ký kết quả vào registry đang chạy, và ghi xuống đĩa để nó vẫn còn ở session sau.

Dòng code quyết định thành bại

Cách viết loop hiển nhiên nhất là compute tool schema list một lần, trước khi loop bắt đầu. Đó là chỗ hỏng âm thầm và vĩnh viễn ở đây: một tool agent tạo ra ở bước 2 sẽ không bao giờ xuất hiện trong schema list gửi cho model, nên nó không bao giờ gọi được thứ nó vừa viết. Cách sửa là self.tools.schemas() được recompute ở mọi iteration — một dòng, và đó là toàn bộ tính năng. Chi phí thật: tool nằm ở đầu prompt trong hầu hết API của các nhà cung cấp, nên đổi chúng giữa chừng hội thoại có thể làm mất hiệu lực prompt cache từ điểm đó trở đi. Nói thẳng ra thay vì giấu đi.

Thực thi code do model viết ra mới là phần thực sự nguy hiểm. Việc kiểm tra được phân lớp — một AST pre-scan từ chối import nằm ngoài một allowlist nhỏ chỉ gồm pure-computation, từ chối truy cập dunder attribute (đường thoát kinh điển ().__class__.__bases__[0].__subclasses__()), và từ chối eval/exec/open; sau đó việc thực thi chạy với __builtins__ đã bị tước bớt. Điều đó nâng đáng kể chi phí để thoát ra ngoài, nhưng không phải là một security boundary — thực thi Python không tin cậy trong cùng process có quá nhiều đường có thể chạm tới để một lớp kiểm tra tĩnh trở nên kín tuyệt đối. Bản production cần cách ly thật sự: một subprocess, seccomp/gVisor, hoặc một container cho mỗi lần gọi. Nói khác đi sẽ là câu duy nhất không trung thực trên trang này.

06 — Ranh giới với Provider

OpenAI là một lớp translation, không phải một bản viết lại

Loop, tool, memory, và trace recorder không bao giờ nhìn thấy wire format của bất kỳ nhà cung cấp nào — chỉ thấy internal representation dạng block của riêng runtime. OpenAILLM convert theo cả hai chiều ở mọi lần gọi, và việc convert đó lộ ra hai khác biệt hợp đồng có thật đáng biết, không chỉ một:

Cái gìInternal shape của runtime nàyWire format thật của OpenAI
System prompttham số riêng của nó{"role":"system",...} làm messages[0]
Tool result cho một turngộp vào một user message duy nhấtmột message cho mỗi result, role:"tool" + tool_call_id
Tín hiệu "model muốn dùng tool"stop_reason == "tool_use"finish_reason == "tool_calls", được chuẩn hóa ngay tại ranh giới

Đảo ngược chiều của tool-result và API trả về 400 — một sự từ chối rõ ràng, không phải một lỗi âm thầm. Đó chính là ý nghĩa của "hiểu thật sự về harness" một khi harness không còn là tài liệu của riêng một nhà cung cấp: contract của loop là bất biến; các byte trên wire thỏa mãn contract đó thì không, và đáng để làm cho đúng tuyệt đối ở cả hai chiều.

Có chủ đích

Streaming, context compaction, concurrency, và subagent đều là những mối bận tâm thật của harness — và đều vượt ra ngoài "tối giản". Transcript serialize được để phục vụ compaction, và on_event là chỗ một streaming UI sẽ hook vào, nhưng thêm chúng vào sẽ đánh đổi đúng cái đức tính được yêu cầu — tối giản — lấy một độ rộng không được yêu cầu. Và một điều self-extension mời gọi nhưng không giải quyết: một agent viết tool rồi sớm muộn cũng sẽ viết ra tool tồi. Không có gì ở đây đánh giá, benchmark, hay loại bỏ một skill đã học — surface chỉ có lớn thêm. Đó là một vấn đề thật, và nó nằm ngoài phạm vi này một cách có chủ đích.
