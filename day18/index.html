Minimal but real · loop, tools, memory

An agent's memory shouldn't only hold facts. It should hold skills.

The brief: build a minimal but real agent runtime — an orchestration loop, tool-calling, and memory, enough to complete a multi-step task. Built one, then pushed it one step further: when the built-in tools can't do what a task needs, the agent writes a new tool for itself, uses it on the very next step, and keeps it for future sessions. One line in the loop is the entire difference between that working and the tool being permanently invisible.

01 — The Loop

A stateless API, turned into something that finishes a task on its own

An LLM API is stateless: you send messages, you get one reply. The runtime is the thin layer that turns that single reply into autonomous, multi-step work — call the model, and if it asks for a tool, run it, feed the result back, and call again. Repeat until the model stops asking for tools or a step cap is hit.

add the user's task to working memory
repeat up to max_steps:
    response = model(system, messages, tools)
    append the response to working memory        # BEFORE acting on it
    if response is not asking for tools:
        return its text                          # the model is done
    for each tool the model asked for:
        result = run it
        collect a tool_result (carrying the tool's id)
    append ALL results as ONE user message
stop: hit max_steps                               # guaranteed termination

The pivot is the model's stop_reason. "tool_use" means the model paused to ask for something; anything else means it produced its final answer. That loop is written by hand rather than through a vendor SDK's tool-runner — the whole point of the exercise is showing the harness is understood, and owning the loop is what makes a step cap, per-step tracing, and total control over tool errors possible.

02 — The Tool Interface

Four fields, and failures that never crash the loop

A tool is a name, a description (the field the model actually reads to decide when to call it), a JSON Schema for its arguments, and the Python function that does the work. A registry turns registered tools into the schema list an API expects and dispatches calls by name.

Failures are data Never an exception into the loop

A missing file, bad arguments, an unknown tool name, a raised exception — all become ToolResult(is_error=True), fed back as a normal tool result the model can read and recover from.

Sandboxed at one choke point No path escapes the workspace

Every file tool resolves the model-supplied path against a fixed root and rejects anything that escapes it. The calculator is a whitelist-only AST evaluator — no names, no builtins, no __import__.

Adding a tool by hand is one decorator:

@registry.add("weather", "Get current weather for a city.",
              {"type": "object", "properties": {"city": {"type": "string"}},
               "required": ["city"]})
def weather(city): ...

03 — Memory

Working memory is context. Long-term memory is knowledge.

Conflating the two is a common mistake, so they're kept apart. Working memory is the running transcript of this task — user turn, assistant turns, tool results, in order. Because the API is stateless, this list is the conversation; it's large, ephemeral, and rebuilt each task.

Long-term memory is a small key/value store persisted to JSON on disk, curated by the model itself through remember / recall tools, and rendered into the system prompt at startup — so the agent begins each session already aware of what it learned before. A fact saved in one session is recallable by a brand-new Memory instance in the next; that's tested, not assumed.

04 — Self-Extension

The tool surface grows mid-task — and one line is why

A meta-tool, create_tool(name, description, input_schema, code), lets the agent supply a tool definition and its own Python implementation. The runtime screens the code, executes it, registers the result into the live registry, and writes it to disk so it's still there next session.

The line that makes or breaks it

The obvious way to write the loop computes the tool schema list once, before the loop starts. That is subtly, permanently broken here: a tool the agent creates at step 2 would never appear in the schema list sent to the model, so it could never call the thing it just wrote. The fix is self.tools.schemas() recomputed on every iteration — one line, and it's the entire feature. The honest cost: tools sit at the front of the prompt in most vendor APIs, so changing them mid-conversation can invalidate a prompt cache from that point on. Stated plainly rather than hidden.

Executing model-authored code is the genuinely dangerous part. The screening is layered — an AST pre-scan rejects imports outside a small pure-computation allowlist, dunder attribute access (the classic ().__class__.__bases__[0].__subclasses__() escape), and eval/exec/open; execution then runs with a stripped __builtins__. That raises the cost of an escape considerably and is not a security boundary — in-process execution of untrusted Python has too many reachable paths for a static screen to be airtight. A production version needs real isolation: a subprocess, seccomp/gVisor, or a container per call. Saying otherwise would be the one dishonest line in this page.

06 — The Provider Boundary

OpenAI as a translation layer, not a rewrite

The loop, tools, memory, and trace recorder never see any vendor's wire format — only the runtime's own block-shaped internal representation. OpenAILLM converts in both directions on every call, and the conversion surfaces two real contract differences worth knowing about, not one:

WhatThis runtime's internal shapeOpenAI's actual wire format
System promptits own parameter{"role":"system",...} as messages[0]
Tool results for one turnbatched into one user messageone message per result, role:"tool" + tool_call_id
"Model wants a tool" signalstop_reason == "tool_use"finish_reason == "tool_calls", normalized at the boundary

Get the tool-result direction backwards and the API returns a 400 — an explicit rejection, not a quiet failure. That's what "true understanding of the harness" has to mean once the harness isn't one vendor's document: the loop's contract is the invariant; the bytes on the wire that satisfy it are not, and are worth getting exactly right in both directions.

What Was Left Out

On purpose

Streaming, context compaction, concurrency, and subagents are all real harness concerns — and all beyond "minimal." The transcript is serializable for compaction, and on_event is where a streaming UI would hook in, but adding them would trade the one virtue asked for — minimal — for breadth that wasn't. And one thing self-extension invites and doesn't solve: an agent that writes tools will eventually write bad ones. Nothing here evaluates, benchmarks, or retires a learned skill — the surface only grows. That's a real problem, and it's outside this scope on purpose.
