Two teardowns: MindPal & PAM

Two product teardowns

Reconstructing two unrelated products, from the outside in

Two exercises in outside-in product archaeology, done back to back: no source code, no internal docs, nothing but public documentation and the live app for each. They don't integrate, don't compete and don't share a customer — MindPal is a general-purpose multi-agent automation platform, PAM is a brand creative-generation tool. Read as two independent case studies of the same method, not as one story.

CASE 1 OF 2

MindPal — general-purpose multi-agent automation

A platform for building AI agents and multi-agent workflows, then handing them either to a team or to the public internet. Its architecture is built around one deliberate seam: everything that needs a login sits above it, everything a stranger on the internet touches sits below it.

The system map

MindPal isn't two products glued together — it's one product with a hard seam running through the middle. Everything above the seam needs a MindPal account; everything below it deliberately doesn't. Drawn as a diagram first, then broken down layer by layer below.

01

Workspace — governance & metering

who's allowed to do what, and who pays
🏢 Workspace

The root container. Owns every Agent, Workflow, Knowledge Source and bill. A person can belong to several.

🪜 Role ladder

Owner → Admin → Editor → User. Editor can create/edit; User can only run what already exists.

OwnerAdminEditorUser
⚡ AI Credit

One metering unit for every LLM call, priced per model (0.5 → 40 credits/request). The only currency in the system.

🏷️ Access Control Tag

Scopes an Editor/User to specific agents or workflows, plus a monthly credit cap per person.

members build inside the workspace
02

Build — the creator surface

requires login · Editor/Owner/Admin only
🤖 Agent

System Instructions + Model + Knowledge/Notes + Brand Voice + Tools/Integrations + Memory. The unit of "one trained AI".

🕸️ Workflow

A canvas of 15 node types chaining agents together — input, routing, evaluation loops, code, payments.

AgentRouterLoopGatePayment
🪄 Mindie

An agent that builds workflows/agents from a sentence. Lives on Home, in the Agent editor, and inside the Canvas.

🔗 Sub-agent

A static delegation link configured once in an Agent's settings — different from an Agent Node, which is assembled per-workflow.

publish — the seam
03

Publish / boundary — not new objects

deployment modes of what's above, nothing more
💬 Chatbot

"The publishable version of an Agent." Same brain, any number of branded, differently-configured front doors.

📝 Form

The publishable version of a Workflow — a hosted web form standing in for the canvas.

⏰ Schedule Trigger

Runs a workflow on a timer instead of a human opening it.

🔌 Public API Trigger

Runs a workflow from another system's server, not a person at all.

anonymous access, zero login
04

Consumption — the public

no MindPal account, ever
🧍 End user

Anonymous by default. Never touches the Owner/Admin/Editor/User ladder — a completely separate identity system.

🆔 Custom User ID

An identifier the host site supplies at runtime (None / Optional / Required) — identity is pushed in, not created inside MindPal.

🧠 Audience Memory

Only turns on when Custom User ID and Audience Memory are both enabled — two independent switches, one feature.

🌐 External systems

Webhook receivers, CRMs, Stripe — where results and payments land outside MindPal entirely.

Five roles, two identity systems

Only four of these five roles ever log in. The fifth — the actual end user — is handled by a parallel, account-less identity mechanism that never touches the other four.

Owner

Full control, unrestricted. Created the workspace; can never be demoted or removed — even by an Admin.

Admin

Near-identical to Owner (billing, members, settings) but cannot touch the Owner's role or remove them.

Editor

Creates and edits everything; can only delete what they personally made. No workspace-settings access.

User

Run-only. No create, edit or delete. Scoped further by Access Control Tags and a personal credit cap.

End user (anonymous)

Outside the workspace entirely. Identified, if at all, by a Custom User ID the host site supplies — not a MindPal login.

Five flows that touch every layer above, in the order a real user hits them.

01Ship one brain, many storefronts

The design decisions behind the architecture

None of this is stated outright anywhere in the docs — it's inferred from what's built, what's priced, and what's kept strictly apart.

1
Chatbot is a deployment mode, not an object

The Agent stays singular and centrally governed; the Chatbot is disposable, brandable, and cheap to multiply. One Knowledge base, unlimited storefronts.

Why it matters: it lets a non-technical team spin up a differently-branded bot per channel without ever retraining or re-uploading anything.

2
AI Credit is the only currency, on purpose

Every action — a chat reply, a workflow node, a scheduled run — draws from the same pool, priced by actual model cost (0.5 to 40 credits).

Why it matters: LLM cost really is fungible across task types, so one unit serves two masters at once — MindPal's own billing, and a workspace owner's internal cost control via per-member credit caps.

3
The role ladder is shaped like an agency, not a company

Editor seats cost $29/mo, User seats cost $5/mo — roughly 6×. Advanced plan explicitly bundles 5 Editor + 20 User seats.

Why it matters: the pricing only makes sense if you assume a small team of builders serving many clients who only ever press "run" — this is agency software wearing a general-purpose skin.

4
Two identity systems that never merge

Workspace membership (Owner…User) and Custom User ID are completely separate mechanisms, and the second is caller-supplied, not self-registered.

Why it matters: a public chat widget needs zero-friction anonymous access, yet still wants personalization — pushing identity ownership to the host site (like Intercom, not like a login-walled SaaS app) resolves that tension without a signup flow.

5
Payment and Webhook nodes sit next to Router and Loop

A workflow canvas that can take money (Stripe, no platform fee as of the current docs) and call arbitrary endpoints is doing more than "chatbot with steps."

Why it matters: it signals the ambition is business-process automation and monetization infrastructure, not just content generation — MindPal is competing with Zapier-shaped tools as much as with chatbot builders.

6
Mindie is the product, eating its own UI

The same assistant that builds workflows also lives on the Home screen and inside the Agent editor — it's the default way to start, not a power-user shortcut.

Why it matters: the node-canvas is a genuinely technical surface; routing first-time users through natural language first is a deliberate onboarding-friction reducer, not a bolted-on gimmick.

7
Public sharing trades relationship-depth for reach, on purpose

Docs state public links get only "limited user history differentiation," while workspace invites get full individual history tracking.

Why it matters: it's a conscious tier, not a limitation — the public path optimizes for anonymous scale, the private path for depth. Audience Memory is the bridge that lets a team have some of both without forcing a login.

CASE 2 OF 2

PAM — brand creative generation

An AI agent that produces on-brand images and video for a marketing team, inside a closed, logged-in workspace. No workflow builder, no public deployment — every screen requires a login and stays there.

The system map

PAM's architecture is two layers, then a hard stop. Everything happens inside a logged-in Brand — there's no third layer where work gets handed to the public, because that layer doesn't exist. The empty space at the bottom of this diagram is the point.

01

Brand — identity & governance

the root container for identity, assets and work
🎨 Brand Kit

Logo, colour palette, typography, guidelines. Folded into every render automatically — no re-stating the rules each time.

🪜 Role ladder

Owner → Admin → Editor → Viewer. Viewer is read-only — there's no "run-only" public tier, because there's nothing to publicly run.

OwnerAdminEditorViewer
🔌 Connectors

Bridges to campaign data, CRM audiences, file storage, publishing channels. Reads run automatically; writes need allow / ask first / off approval.

📓 Playbooks

A saved creative recipe a team reuses. "Guides a run; it doesn't freeze it" — the agent still adapts it to each new brief.

members brief the agent inside the brand
02

Work — session → brief → artifact

requires login · Editor/Owner/Admin only
💬 Session

One conversation with the brand agent. One brief can fan out into several artifacts; a new session starts context-clean.

📋 Design Brief

The agent's structured plan — goal, exact copy, target sizes, tagged references. The user must confirm it before anything renders.

🖼️ Artifact

The finished image or video. Editing or regenerating never creates a new tile — it appends a version to the same one.

🕐 Version

Linear history, images only — step back, compare, or restore. Video artifacts don't carry versions; regenerating or animating again is the only way to redo one.

and that's the whole system
03

It stops here

there is no third layer

No Chatbot, no Form, no API Trigger, no Schedule Trigger, no anonymous end user — nothing in PAM ever leaves the logged-in workspace. The gallery is the end of the line: a human downloads the finished artifact and posts it themselves, wherever it needs to go.

Four roles, no public tier

Every one of these four logs in with V-ID. There's no fifth, account-less role — PAM stops at Viewer.

Owner

Full control, including billing, deleting the brand, and granting ownership to someone else.

Admin

Manages members, connectors, and brand guidelines & content. One step below Owner.

Editor

Creates and edits artifacts, runs the AI agent. The production role — where most work happens.

Viewer

Read-only access to the workspace. Can look, can't touch — the closest thing to an outsider, and still fully logged in.

— no public role —
nothing outside the login wall

The jobs this architecture is built to do

Four flows that touch every layer above.

01Brief once, compare variants before committing
Editor types a brief in the composer
agent drafts a Design Brief — goal, copy, sizes; Editor confirms it
4 Directions render, then several Concepts per chosen direction
picked concept lands in the gallery as an Artifact — final touches from there
02Iterate without losing anything
open an Artifact in the lightbox
Edit, Resize, Animate or Regenerate — each appends a new Version
step back to any earlier version to compare or restore
nothing is ever deleted by trying a bolder edit
03Reuse a house style across a whole team
someone writes a Playbook once — style, structure, constraints
any Editor picks it when starting a new run
agent adapts the saved recipe to that day's brief
consistent output without re-explaining the house style each time
04Audit what happened, without redoing it
Admin / Owner opens the Sessions rail
picks a past session, hits Replay
walks back through the agent's reasoning, step by step
read-only — nothing re-runs or changes

The design decisions behind the architecture

Inferred from what's built, gated, and left out — not stated outright anywhere in the docs.

1
The Design Brief is a mandatory gate before anything renders

The agent must draft goal, exact copy, sizes and references — and the user must confirm that plan — before a single pixel gets generated.

Why it matters: catching a wrong direction at the cheap text stage is far less costly than catching it after four rendered concepts. It front-loads correction to where it's cheapest.

2
"Workflow" means a fixed route, not a canvas

Create / Adapt / Animate / Sandbox / Auto are five pinned pipelines the agent selects — there's no node-by-node builder anywhere in the product.

Why it matters: PAM's audience is brand and creative teams who want a result, not engineers assembling a pipeline. Presets trade flexibility for zero setup cost, keeping the tool approachable for people who've never built an automation in their life.

3
Versions are linear, never branching

Edit, Resize and Regenerate all append to one timeline per image artifact — there's no fork/branch concept anywhere. Video is the one exception: once rendered, a video doesn't carry further versions of its own.

Why it matters: creative iteration is usually one lineage getting refined ("make it warmer," then "now resize it"), not parallel experiments. Linear history matches how a person actually works, and "nothing is lost" removes the fear of trying a bolder edit.

4
There is no publish layer, anywhere, on purpose

Every single screen sits behind V-ID login. No public link, no embeddable widget, no anonymous visitor of any kind exists in this product.

Why it matters: the finished asset is the brand's IP. A creative-ops tool's output is meant to leave through export and get posted deliberately — not through a hosted public surface where an on-brand asset could be generated in an uncontrolled context.

5
Connectors gate writes but not reads

Look-ups (checking campaign performance) run automatically; anything that publishes or sends somewhere needs allow / ask first / off approval per action.

Why it matters: a deliberately asymmetric trust model — low-risk information retrieval stays frictionless, while anything that could leak brand content externally keeps a human in the loop by default.

6
Replay is restricted to Admin and Owner, not Editor

Any Editor can create; only Admin/Owner can walk back through how the agent reasoned on a past session.

Why it matters: Replay is an oversight feature, not a creative one. Gating it to the roles accountable for brand governance keeps it aligned with what it's actually for — accountability, not reuse.
